# F49-D.02-FU-SLOTS (#1629): the original's per-slot Instant Action loadout selection

Task #1629, branch `rally/1629-model-the-original-s-per-slot-instant-ac`.
Follow-up of #1575 (`docs/findings/2026-10-18-f49-d-02-fu-loadout-identities.md`),
which measured that `ORDINANCELAYOUT.SCRIPT` edits gun/ammunition/rocket slots by
integer index and that no loadout identity list exists. This task measured the
per-slot choice ranges and default contents, and modeled them in production code.

## Measured

### The actor record the editor edits

The Instant Action plane record is `0xcc` bytes; the ordnance fields are:

| offset | contents |
| --- | --- |
| `+0x2c` | plane id = airframe-table index |
| `+0x34` | first rocket-bank count (slots `0..n`) |
| `+0x38` | second rocket-bank count (slots `4..4+n`) |
| `+0x84` | paired-gun bitmask, bit per gun slot (byte) |
| `+0x88` | gun ids, `4` slots; `5` = slot absent |
| `+0x98` | ammunition kinds, `4` slots; `4` = no ammunition |
| `+0xa8` | rocket ids, `8` slots; `11` = none |

Editing is staged through a pending buffer (`0x6480cc`, `0x33` dwords):
callback `2035` (`0x4095d3`) copies the selected actor's record in, `2034`
(`0x409578`) copies it back. The actor selector `ZQ` is `-1` (player) or `-2`
(wingman); for Instant Action the live records are `0x64abf4 + actor*0xcc`.

### The `$$E$$` callbacks (dispatch table `0x40f5b4`/`0x40f788`, shared frame `0x4093a0`)

| id | handler | measured behavior |
| --- | --- | --- |
| `2027` | `0x409a5c` | gun-ammunition dropdown: count fixed at `5` (immediate store at `0x409a65`); item `n` labeled `3360 + n` (`ammo_short_name` block). Item index = stored kind. |
| `2028` | `0x409b72` | rocket dropdown: count = number of *available* selector rows (`0x40ff00`); item `n` labeled `3395 + id` where `id = 0x40ff50(n)` is the n-th available row. |
| `2030` | `0x4099f2` | gun-slot query: returns the record's gun id (`+0x88`), writes the gun name (`3320 + id`) and the slot's current ammunition kind (`+0x98`). Return `5` greys the slot (script compares against `5`). |
| `2031` | `0x409aec` | rocket-slot query: writes the name (`3395 + id`), returns the dropdown index of the stored id (`0x40ffa0`), or `-1` for a slot outside the record's bank counts — which greys the slot. |
| `2032` | `0x409a93` region | ammunition description area: string `3350 + kind` (`ammo_long_name` block). |
| `2033` | — | rocket description area: string `3380 + id` (`IDS_ROCKETLONGNAME` block). |
| `2034` | `0x409578` | apply: copies the pending buffer into the actor's live record. |
| `2035` | `0x4095d3` | begin: copies the actor's live record into the pending buffer. |
| `2036` | `0x40962c` | set gun ammunition: stores the item index raw at `+0x98 + 4*slot`. |
| `2037` | `0x409654` | set rocket: maps the item index through `0x40ff50` (n-th *available* row) and stores the rocket id at `+0xa8 + 4*slot`. |

### The per-slot choice ranges

* **Gun slots (4).** The gun in each slot is fixed by the airframe template —
  the screen offers no gun picker; slot `n` exists iff its stored gun id is not
  `5`.
* **Gun ammunition (4 selectors).** Every gun slot's dropdown offers the same
  five kinds `0..=4`, item index = stored kind. Kind `4` is "no ammunition"
  (`gun_loadout` at `0x41bca0` answers `ammo_none` for it) — the value every
  absent slot's template entry holds.
* **Rocket slots (8, two banks).** Slot `n < 4` exists iff `n < +0x34`;
  slot `n >= 4` exists iff `n - 4 < +0x38`. Each present slot offers the
  *available* rows of the selector table at `0x619efc` — twelve rows of eight
  bytes indexed by rocket id `0..=11`, row `11` = "no rocket".

### The rocket selector table (`0x619efc`, committed as `ORIGINAL_ROCKET_SELECTOR_ROWS`)

`gate` is the availability threshold: the row is offered when
`gate <= progress + 1`, where `progress` is the cell at `0x64b678` — the
running maximum of the mission index written through native `2104`, clamped
to `24`. Any of the three globals `0x647b5c`, `0x647b68`, `0x647b6c` opens
every row. The second dword (`aux`) is **unmeasured**: no reader was reached.

| id | gate | aux | | id | gate | aux |
| --- | --- | --- | --- | --- | --- | --- |
| 0 | 1 | 4 | | 6 | 7 | 2 |
| 1 | 1 | 4 | | 7 | 7 | 4 |
| 2 | 2 | 2 | | 8 | 17 | 4 |
| 3 | 8 | 2 | | 9 | 17 | 1 |
| 4 | 7 | 2 | | 10 | 20 | 0 |
| 5 | 12 | 2 | | 11 | 1 | 0 |

At progress `0` the offered ids are `{0, 1, 11}` — two rocket types plus
"none". What progress an Instant Action session sees is the session's
campaign cell; Instant Action itself writes no progress value found in this
pass.

### Default slot contents (roster templates `0x619f58`, stride `0xcc`)

Committed as `cs_content::weapons::ORIGINAL_AIRFRAME_LOADOUTS`, keyed by the
airframe table's `scene_root` (index order of the airframe table `0x620c70`,
the same index order `data/owner-static/engine-facts.toml` records). Instant
Action copies the selected plane's template into the actor record (the
`0x41034a` initializer and plane-change handlers `2313`/`2317` at `0x40c229`),
so these are the contents the editor opens with. Examples:

| airframe | guns | ammo | rockets | banks |
| --- | --- | --- | --- | --- |
| `player_pfighter` (5) | `[2,1,0,5]` | `[0,0,0,4]` | `[1,1,11,11,1,1,11,11]` | 2/2 |
| `player_warhawk` (10) | `[4,2,5,5]` | `[0,0,4,4]` | eight `1`s | 4/4 |
| `player_autogyro` (0) | `[0,5,5,5]` | `[0,4,4,4]` | `[1,11,11,11,1,11,11,11]` | 1/1 |

Templates `11`/`12` are the fresh-profile player/wingman copies of the
Devastator record (F27-M). Default ammunition is always kind `0` on a present
slot; default rocket id `1` on a present slot.

## The production model

`cs_content::instant_action::SlotOrdnance` is an actor's ordnance in the
original's terms: `gun_ammo[4]` + `rockets[8]` integer picks, range-checked
at `try_new` against the measured domains. `ScenarioActorSpec::with_slot_ordnance`
attaches it; `InstantActionCatalog::validate_custom` then checks each pick
against `weapons::original_airframe_loadout(actor's scene_root)` — the same
slot-presence tests `2030`/`2031` apply — and reports
`ScenarioProblemCode::ImpossibleSlotChoice` for a pick in a slot the airframe
lacks or on an airframe with no measured template, and `ConflictingOrdnance`
for a named loadout beside the slots. When a `SlotOrdnance` is attached the
named-loadout requirement is satisfied: an `Unknown` loadout then reports no
unmeasured field. `weapons::original_offered_rockets(progress, override)`
reproduces the gate rule.

## Unknowns recorded, not filled

* `aux` (the selector row's second dword): unmeasured, no reader reached.
* The three globals `0x647b5c/0x647b68/0x647b6c` that open every row: their
  *names* are not measured (they read like unlock-override flags; plausible
  cheat or profile unlocks, not asserted).
* Whether an Instant Action session ever sees progress `> 0` is a session-state
  question (the gate reads the campaign cell); the original run question stays
  open.
* Lowering `SlotOrdnance` into a spawned scenario is not in this task's owner
  paths — `LOADOUT_RESOLVING_TASK` now names it.
