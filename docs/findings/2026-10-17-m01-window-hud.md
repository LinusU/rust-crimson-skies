# M01-WINDOW-HUD: why the windowed M01 showed no objective, subtitles, and whether M01's opening has music

Date: 2026-10-17. Task: #1539. Capabilities: `retail`, `gpu`, `audio` (windowed run
on the owner's machine, `CS_MISSION_CAPTURE=1`). Nothing here is `verified_original`.

## 1. Objective line

Reproduced the owner's playtest: the window showed only the telemetry block and the
key-help strip. Cause: `ObjectiveHudPlugin` drew `ObjectiveHud::current()`, the row
the lifecycle model marks *live*. Every M01 identity block loads dormant and the first
(OBJECTIVE9) wakes only through the record's wake chain, so at launch, and between two
objectives (the latch hops OBJECTIVE10 -> 49 -> 50 -> 11), nothing was live and the
line was hidden. #1462's tests pinned that hidden state.

Fix: `ObjectiveHud::displayed()` returns `current()` when one is live, otherwise the
pending identity (role code nonzero, not completed) with the smallest rank. The widget
draws `displayed_text`. `current()` and its tests are unchanged. The choice is
**designed** (unmeasured what the original shows while nothing is awake; the layout was
already labelled designed) and resolves with the same original-run evidence as #1462's
unknowns 1 and 2. The text is the installation's own `strings.dll` row; the caption is
now plain ASCII because the em dash rendered as a missing-glyph box in the window font.

Windowed capture after the change (kept in `private/`, not committed): the first line
is drawn from frame 1 under the telemetry block. The retail text for MSG_BRF_NWM1_OBJ1
is a different wording from the four titles in the task description ("Find the main
treasure site", ...); those are not in the data, the data's own text is shown.

## 2. Radio subtitles

Unchanged verdict of `2026-10-15-m01-play-radio-dialogue.md` section 4: no key maps a
voice member or sound-group name to caption text (re-checked: `voice.zrd`, `Dialog.zrd`
and `dlgMessage.zrd` hold no prose; only the `MSG_BRF_*` ids resolve, and they are
objectives, not voice lines). So no subtitles are shown; none are invented.

## 3. Music

Measured by `accept_m01_music_state_requests_*` (#1463): M01 spells five `music_*_sg`
states, and every one is on a block that wakes only as another block's
`WAKE_OBJECTIVE_WHEN_I_COMPLETE` effect, so none is cued by the mission clock in the
opening. The windowed run's launch (two captures, ~3 s of flight) matches: no music
request is expected there. Music therefore starts at objective transitions, not at
mission start.

Those requests reach `MusicDirector`, but `AudioSession::request_music` has no
playback consumer (#1463 finding, section 6 item 3): no mixer or device routine plays a
`MusicOutcome`. That is why nothing can be heard at the transitions either. Making it
audible needs the track decode, a looping music bus and device wiring, a slice of its
own, filed as a follow-up task.
