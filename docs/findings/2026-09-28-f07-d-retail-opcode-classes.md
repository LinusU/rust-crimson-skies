## Design decisions

- **Three classes, and absence is not one of them.** `OpcodeClass` is
  `Loading { arguments, spelling_kind }` (the plan spells the line's key from
  named stored arguments), `Unsupported` (recognized as bringing content in,
  but with no mount-namespace key this stage can spell) and `Behavior` (not a
  resource load). A head no classification names is **unknown**, and an unknown
  line blocks its world. The table refuses a duplicate spelling, an empty
  spelling, an empty provenance, a self-awarded `verified_original` and a
  `Loading` entry whose argument positions cannot spell a key, exactly as the
  F07-C `LoadCommandTable` does.
- **The audit is a checked property.** `audit_interp_opcodes` walks every line
  and reports one entry per distinct head — spelling, occurrence count and
  class (or `unknown`) — in spelling order. `OpcodeAudit::is_complete()` is
  true only when no head is unknown, so "classify every opcode" is something a
  caller can check rather than assert. The CLI adds an `opcode_audit` section
  and exits 3 while any head is unknown, so an incomplete classification is
  never reported as success.
- **Classification is separated from resolution, still.** `cs_formats` builds
  no keys and touches no filesystem; `plan_interp_loading_classified` names the
  class and the argument positions, and `cs_content::loading` turns a `Loading`
  line into an asset key and a dependency. `Unsupported` and `Behavior` need no
  session at all.
- **A `Behavior` line does not block; an `Unsupported` line does.** A world is
  not unloadable because a camera or scene command sits beside its loading
  commands, but it *is* unknown while a resource it needs cannot be spelled.
  That is the difference between "this contributes nothing" and "this
  contributes something we cannot name", and the plan keeps them apart.
- **The CLI gained a flag, not a command.** `--classes` subsumes `--commands`
  (a `loading` entry carries the same rule) and the two are mutually exclusive,
  so one line never has two sources of truth. The report keeps its `commands`
  array and gains `opcodes` and `opcode_audit`.

## Method, and why there are no `loading` entries

The `Unsupported` versus `Behavior` line follows the argument shapes observed
over the whole corpus (`private/f07d_heads.txt`, a read-only dump; not
committed). `docs/findings/2026-09-28-f07-c-loading-plan-adapter-and-dependency-tracing.md`
already established that the vocabulary is scene-graph and terrain work, and
that nearly every path-shaped command interpolates `%NAME%` variables defined
by earlier `set` lines.

- **`unsupported`** (20) are the commands observed to name content by a path,
  directory or `%VARIABLE%`, with no `namespace path` pair this stage could
  spell as a mount-namespace key: `LoadGameGen` (a model file *and* an alias
  name, not a namespace), `CycleTextureSetMap` (one texture path),
  `LoadSoils` (one `.zrd`), `SetModelDirectory`, `SetTextureDirectory`,
  `RdrAddPath`, `RdrSetPath` (search directories), `mkdir` (one directory),
  `source` (a script include), `GameZReadZBDFile` / `GameZWriteZBDFile`,
  `AnimSetZRDRFile` / `AnimSetZBDFile` / `AnimAddZBDFile`,
  `PrintUsedTextures` (an output directory), `GameGenTranslatePaths` (a path
  prefix), `WriteTextureSetMap` (an output texture), `DeleteFile` (one file),
  `LensFlareTexture` (an index plus a flare texture) and `LightMapTexture` (a
  texture name).
- **`behavior`** (65) are the rest: scene-graph (`FindNode`, `AddChild`,
  `FindSubNode`, `DeleteChild`, `DeleteTree`, `NodeSetActive`,
  `NodeSetDescription`, `Object3D*`, `NewObject3D`, `CreateUniqueMaterials`),
  terrain and world setup (`World*`, `AddClutterTemplates`,
  `SetIntersectSurface`, `SetAltitudeSurface`, `LoadSoils`'s siblings), camera
  and display (`Camera*`, `NewCamera`, `NewWindow`, `Window*`, `NewDisplay`,
  `Display*`), lights (`LightNew`, `LightSetActive`, `WorldAddLight`,
  `WorldSetFogState`), tuning parameters (`MipBias`, `SetBFETolerance`,
  `SetCoplanarTolerance`, `SetColinearTolerance`, `SetInverseZTolerance`,
  `PerspectiveTexture`, `SetPerspective*`, `SetSmallPolygonRejectArea`,
  `GameGenSetSubfacePriorityOffset`, `VideoSetDither`, `Object3DRotate`,
  `Object3DTranslate`, `Object3DSetScroll`, `CycleTextureSetOn/Speed/Looping`)
  and the language's own control flow and variables (`set`, `ifdef`, `ifndef`,
  `endif`, `Quit`).

There are **zero `loading` entries** because no observed head names a key as a
`namespace path` pair; every content-bearing command takes a single path, a
directory or a `%VARIABLE%`. This is the honest result, not a gap: the F07-C
finding said the retail corpus "needs a variable model, not a bigger table",
and F07-D's job is to say so, not to force a key onto a command that does not
have one. The `loading` class is exercised end to end by the synthetic tests
(`accept_f07_d_loading_registry_maps_to_loading_classifications`,
`accept_f07_d_cli_audits_every_head_and_reports_completeness`).

### Ambiguities, recorded rather than hidden

- `FindSubNodeNode` takes a `.flt` spelling (`zep_main_dstry1.flt`) but its
  name parallels `FindSubNode`, whose arguments are node names. It is
  classified `behavior` (a scene lookup whose argument happens to look like a
  file). If F13 shows it loads a model, this entry is wrong and moves to
  `unsupported`.
- `GameZWriteZBDFile`, `WriteTextureSetMap`, `PrintUsedTextures`, `DeleteFile`,
  `mkdir` and `GameGenTranslatePaths` are filesystem *side effects* or path
  configuration, not reads. They are classified `unsupported` because their
  arguments are paths/directories this stage cannot spell as keys; they block
  their world conservatively. Whether the shipping engine treats them as
  loading-system or tooling commands is unmeasured.
- Every classification carries `ClaimStatus::Inferred`: it is an inference
  from the observed head name and argument shape over one installation, not a
  documented opcode list from the original vendor. No `verified_original`
  status is awarded anywhere.

## What is still unknown

- The mission language's opcode semantics (what each command does at run time,
  not just whether it names content) remain F13's subject; F07-D classifies
  loading behaviour only.
- The vocabulary of the loading language's variables (`%ZBD_DIR%`,
  `%CAMPAIGN_DIR%`, `%MISSION_DIR%`, `%DATA_DIR%`, ...) and their substitution
  rules are unmeasured, so a literal-key resolver has nothing to resolve for
  the 20 unsupported commands. This is why they are `unsupported`, not
  `loading`.
- Argument and name encodings are still not established; the report keeps every
  byte string as length plus hex.
- Whether `LoadGameGen`'s second argument is an alias or a second key part is
  unmeasured; treating it as a `namespace path` pair would be a guess.

These are recorded here and filed as follow-up tasks; they are not asserted as
understood.
