Date: 2026-10-10. Task: EVIDENCE-CONTENT-DIGEST-OUTLIERS "Three committed
evidence reports carry a content_sha256 production discovery does not
reproduce" (#1157), filed by bunny-alpha-2 while regenerating reports under
#804. Contract: `schemas/evidence.schema.json` with
`docs/contracts/CLI-EVIDENCE.md` ("installation/canonical-content hash" in
the evidence record minimum). Capabilities used: `retail` (`$CS_GAME_DIR`
read-only, never written). Implementer: **Devin SWE-2/swe2-max-1** (Rally

`verified_original`: this note compares committed JSON against production
digests of the read-only installation; no original executable was run.

## What the field means

`source.content_sha256` is the installation's canonical-content
fingerprint: `cs_assets::install::content_fingerprint`, documented in
`crates/cs_assets/src/install.rs` as "the `content_sha256` of an evidence
record (`schemas/evidence.schema.json`)". It is SHA-256 over the per-file
content digests of **every** manifest row, sorted by logical key — the
whole installation, not the subset a stage exercised.

Re-measured on this host (2026-10-10) through the production path —
`cs-inspect inventory --cs-path "$CS_GAME_DIR"`, which prints
`install::fingerprint` and `install::content_fingerprint` of the discovered
manifest:

| Field | Production value |
| --- | --- |
| `install_sha256` | `b4e780ab84cf31d85b8452fbfcec1478137768e32d9a75ccedc4c1847c631978` |
| `content_sha256` | `a0223506e512b50c0e0445ba73204a0461e60197e28d58a7f7144632d262c12d` |

152 of the 156 committed reports carry exactly this pair (one more,
F52-D, carries `null`/`null` — a report measured over no installation).
The three outliers below carry the same `install_sha256` but a different
`content_sha256` — which cannot come from one run over one manifest, since
both fingerprints are pure functions of it.

Each recorded value is therefore a deliberate *task-scoped* digest — the

meaning is the whole-installation fingerprint. This matches the "different
scope/algorithm" hypothesis of the task description; the "stale relative
to the runs" alternative is ruled out, because each value deterministically
re-derives from the same installation bytes the matching `install_sha256`
describes.

## The findings (the harness bug the task predicted)

1. **Scoped digest in a canonical field.** Each of the three private
   writers computed `source.content_sha256` over the subset of content its
   stage exercised — two container files (F05-D), two decoded members
   (F12-J), 65 member stored digests (T351) — instead of
   `content_fingerprint(manifest)` over the whole installation. That is a
   real bug in those harnesses: a reader comparing the field against
   production discovery gets a mismatch nothing in the reports explains.
2. **T351's `review.method` additionally misdescribes its own input.** It
   says the harness "re-derives `content_sha256`" from "per-member decoded
   digests", but the recorded value is over the members' **stored** extent
   digests — the `members[].sha256` roster field of `cs-inspect rof`, which
   is the SHA-256 of the stored extent. All 65 members are compressed, so
   stored ≠ decoded for every one of them (the same computation over the
   decoded digests gives `fa0663c5…`, not the recorded value).
3. **Uncommitted writers made the reports unreproducible.** None of the
   three reports could be regenerated when this was written: the two
   `harness.py` scripts and F05-D's ad-hoc sequence lived in `private/` on
   the producing hosts and are gone. The review-identity checker only
   cross-checks a committed report against a committed harness it can find;
   a report with no committed harness gets no regeneration cross-check,
   which is how three divergent field semantics shipped unchallenged.
   (Rally #1174 closed this one: since the repair each of the three reports
   has a committed harness, and `test_evidence_review_identity.py`
   cross-checks all of them.)

What this is **not**: not installation drift (`install_sha256` matches
everywhere, and the values re-derive deterministically from the same
bytes), and not a production bug (`discover` + `content_fingerprint`
answers `a0223506…` as documented).

## Resolution

This task's acceptance criteria allow either regenerated reports whose
`content_sha256` equals production, or the divergence explained with
evidence here. #1157 took the explanation branch and left the three
reports byte-identical — the contract forbids hand-editing them — because
no committed writer existed for any of them, and F05-D's
`reference-comparison.json` had been produced by an ad-hoc sequence that
was never committed, so its original bytes could not be regenerated by
any option (the pinned S05 extractor, commit `214b170b…` / file sha256
`96374b5d…`, was simply not in the checkout either).

**Repaired by Rally #1174 (`EVIDENCE-CONTENT-DIGEST-OUTLIERS-REPAIR`) on
2026-10-10, owner decision (a):** all three reports were reissued through
the committed harnesses `crates/cs_app/tests/campaign/evidence/f05_d.rs`,
`…/f12_j.rs` and `…/t351.rs`, each run through the four-step sequence its
module doc documents.

- `source.content_sha256` in all three is now
  `cs_assets::install::content_fingerprint` over the manifest production
  discovery reads — the canonical `a0223506…` every other committed report
  carries — measured by the harness, never copied in. The scoped values
  above are unchanged as *records*: they stay in the table above and in
  the sentinel's `REISSUED` table, and each still re-derives from the
  installation through production code in
  `accept_evidence_content_digest_outliers_each_documented_scoped_digest_still_re_derives`.
- `review.identity` is byte-unchanged in all three reports; the
  regeneration facts are appended to `review.method` instead, per the #804
  convention and the owner's decision. Run facts — `candidate_tree`,
  `created_at`, `command.cwd`, the test counts, the assertions and the
  artifact digests — are the reissue run's own.
- Artifacts: F05-D's two `cs-inspect rof --audit` reports reproduce the
  digests the original report recorded byte for byte (`c00357ba…` and
  `55f9be89…`), and T351's `rof-read-layout.json` reproduces `d64f5b23…`.
  F05-D's `reference-comparison.json` is a **fresh artifact in the new
  harness's documented format** — the original bytes are unrecoverable
  because the ad-hoc sequence was never committed — and it compares the
  pinned S05 extractor's per-file sha256 digests against the production
  reader's decoded digests, member by member, over both containers (847
  members); the extractor is re-fetched from its public upstream and
  sha256-verified against `96374b5d…` before every use, patched only in
  its `ROF_PATH` constant, and never committed. F12-J's three artifacts
  are fresh as well: each embeds this installation's `host_root`, where
  the original run recorded the producing host's, so equivalent content
  hashes differently on this host.
- **Sentinel:** `accept_evidence_content_digest_outliers_*` in
  `crates/cs_app/tests/accept_evidence_content_digest_outliers.rs` now
  pins an **empty** outlier set: any report whose `content_sha256` is not
  this installation's canonical fingerprint fails, each scoped value is
  still re-derived through production code rather than allowed, and the
  two `…_repair_` tests fail if a reissued report regresses, loses its
  regeneration note or stops naming the committed harness that writes it.
  There is no allowlist to remove a report from any more: the outliers are
  gone, and a scoped digest coming back fails immediately.
- **Validation:** all three reports were regenerated on this tree and pass
  `python3 tools/validate_evidence.py private/evidence/<TASK>/acceptance.json
  --artifact-root private/evidence/<TASK>` — with `--require-pass` for
  F05-D, without it for F12-J and T351, whose recorded unknowns must stay
  recorded (their `unknowns` are unchanged). Their own acceptance
  selections pass on this tree with the retail capability:
  `cargo test --workspace --locked -- accept_f05_d_ --include-ignored`
  (7 tests), `accept_f12_j_` (3 tests — the original report recorded 2; a
  third exists today) and `accept_t351_` (5 tests), all passing, the
  retail tests included.

Nothing here is `verified_original`: no original executable was run and
no human saw or played anything, so the merge awards `checked` only. The
nine unknowns T351 records and the one F12-J records stay open with their
resolving tasks, exactly as before the repair.
