# M01 audio: what static analysis says about the source of the 33,864 B loop

Task #2030 (PARITY6-M01-AUDIO-33864-SOURCE), split from #2002. Claim id
`OWNER-STATIC-2026-10-24`, provenance `static` (decrypted engine image plus
retail files; disassembly kept in `private/`, not committed). Nothing here is
`verified_original`, and no original run is involved.

**Result: the source is not identified.** Three candidate families are ruled
out, and the length rule of every route into the buffer creator is now cited.

## What `zsnd_cd.cpp` is: not a buffer source

Its `__FILE__` string is at `0x63a5bc`; the words `cdaudio` (`0x63a5e0`),
`CDAudio` (`0x63a5e8`) and `MCIError` (`0x63a5f8`) follow it. All 14 uses of the
path lie in `.text` `0x598175..0x598dd2`. That range calls `mciSendCommandA`,
`mciGetErrorStringA`, the `mixer*` and `aux*` volume calls and nothing else
audio-related; it calls none of the source constructors, the dispatcher
`0x59b580` or the creators `0x59b5e0` / `0x59b950`. It plays CD tracks through
MCI. It never produces PCM and cannot own a 33,864 B DirectSound buffer.

## Every route into the buffer creator (`.text` call sites, exact)

The dispatcher `0x59b580` (callers `0x5965b2`, `0x596d1d`, `0x596dd3`,
`0x59bfd0`) takes a source object and creates the buffer with the length word
`[src+0x10]` (creator `0x59b5e0`, see the #2002 finding). A source is built by:

| Constructor | VA | Callers | Bytes come from |
| --- | --- | --- | --- |
| from a name, flag 1 | `0x59afc0` → `0x59b3f0` | `0x596598` | `fopen(name, "rb")`; names starting `mu` are skipped |
| from a name, flag 0 | `0x59afc0` → `0x59b4f0` | `0x596cf8`, `0x596dae` (reads at `0x596d11`, `0x596dc7`) | a reader object (the `soundsH/M/L.zbd` archive named at `0x63a544..`) |
| from memory | `0x59b010` | `0x5cff6c` | a file image read by name through `0x5d0100` |
| from raw memory | `0x59bf80` | `0x5cff7d`, `0x5f9483`, `0x5f954b` | `(format, data, length)` triple |

All of them end in the same two steps: the RIFF walk `0x59b090` and, when the
format tag is not 1, the ACM decode `0x59b170`.

## The length rule of `[src+0x10]`

* **PCM (tag 1):** the `data` chunk's declared size (`0x59b108..0x59b11c`
  stores the data pointer at `+0x28` and the size at `+0x10`). The first `data`
  chunk wins.
* **Anything else:** `acmMetrics`, `acmFormatSuggest`, `acmStreamOpen`,
  `acmStreamSize(SOURCE, data size)`, then `acmStreamPrepareHeader`,
  `acmStreamConvert` and `acmStreamUnprepareHeader`. The code then stores
  `[ebp+0x10] = [ebp+8] = ` the **`acmStreamSize` result** (`0x59b3a2`,
  `0x59b3aa`), not `cbDstLengthUsed`. The length is therefore the driver's
  size *estimate* for the stored data size. For the MS ADPCM members the
  owner's other logged sizes match the whole-block rule (119,416 = 59 × 2,024);
  the estimate of a driver on the owner's machine for a trailing partial block
  or for IMA data is **not** observed.
* `cue ` chunks only fill `[src+0x1c]`/`[src+0x20]` (cue count and points,
  rescaled by the rate ratio at `0x59b2ab..0x59b2f2`); they never cut the data.

## Ruled out

1. **A member of `soundsh.zbd` / `soundsl.zbd`, `crimson.rof` or
   `SETUPENU.DLL`.** No blob decodes to 33,864 B or half of it. Besides the
   earlier whole-block rule, every ADPCM blob was also measured with an exact
   partial-block size and with the range between the two readings: none of them
   brackets 33,864 (5,029 of 5,030 ADPCM blobs are whole blocks; the one with a
   partial trailing block does not bracket it either).
2. **A compressed member of any `.zbd` / `.rof`.** The raw RIFF scan of #1861
   cannot see zlib members. A scan of every zlib stream in all `.zbd`/`.rof`
   files (706 streams that inflate cleanly) found **no WAVE** among them.
3. **A loose `.wav` file.** The install has none (file types: 184 `.zbd`,
   18 `.dll`, 10 `.mpg`, 3 `.exe`, 2 `.tga`, 2 `.rof`, plus setup files).
4. **The FMV audio.** `fmv_stream.cpp` (`0x5f9340..0x5f954b`) builds an AVI
   sound buffer whose size is `AVIStreamLength × dwSampleSize` (`0x5f94b8`) or,
   when streaming, twice `dwSuggestedBufferSize` (`0x5f9404`, `0x5f947e`), so
   its sizes are not on an ADPCM lattice. But all ten retail `.mpg` movies carry
   MPEG-1 Layer II audio at **44.1 kHz** (mono or stereo), not the 11,025 Hz of
   the loop, so this route does not explain the owner's 11,025 Hz → 22,050 Hz
   buffer unless the AVI handler resamples (not observed).

## Still unknown (rule 4)

* The source of the 33,864 B (16,932-sample) buffer. Affected content: the
  owner's 15.0 s voice in M01 and its rate step.
* The `acmStreamSize` estimate of the owner's ACM drivers for IMA ADPCM data
  and for partial trailing blocks (one retail MS ADPCM blob has a partial block and
  does not bracket 33,864; IMA blobs are all whole blocks).
* Which caller of `0x59bf80` / `0x5d0100` (the `0x5d631b..0x5d6cf6` readers of
  `0x5cff30`) names the file; a dynamic view of the owner's run would settle it.

The sound-source members of the owner's log that ARE matched (#1861) are
unchanged by this finding.
