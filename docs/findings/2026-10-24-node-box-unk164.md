# The container node box (`unk164`): meaning, frame, and what is not proven (#2048)

Date: 2026-10-24. Task: #2048, part of #2017 item 5. Capability used: `retail`
(read-only `$CS_GAME_DIR`) and the owner-supplied engine image (`$CS_ENGINE_IMAGE`,
static reading only). Nothing here ran the original executable; nothing is
`verified_original`. Tests: `accept_m01_convoy_gun_hits_` in
`crates/cs_app/tests/campaign/m01_convoy_gun_hits.rs` (retail one is `#[ignore]`).

## 1. What the box is, from the image (static)

`docs/findings/2026-10-08-m01-lc-world-residual-roles.md` already showed that the three
24-byte boxes of a node info record (`unk116` / `unk140` / `unk164`, offsets 116 / 140 /
164) are selected by the record's `unk112` word (0 / 1 / 2) and that the selected one
is the only non-empty one. Every node this task cares about has `unk112 = 2`, so
`unk164` is the box, and it is empty in the other two slots (read through
`RawNodeInfo`, all of `t_truck01`, `t_truck03`, `bridge_truck01`, `susp_bridge`,
`rock_zeppelin`).

The database-intersection walk (`cls_di.c`, VA `0x4cb950`; its narrow-phase branch is
`0x4cb665`) does this with the selected box:

| step | what it does | address |
| --- | --- | --- |
| copy the 24 bytes at `node+0x70` (the selected box) | `rep movsd` x6 | `0x4cd960` |
| expand min/max into the **eight corners** (24 floats) | `mov` pairs from the six values | `0x4cb8b0` |
| carry the eight points through the **current matrix** (3x3 at `+0x00..0x20`, translation at `+0x24..0x2c`) | `fmul`/`fadd` per point, count 8 | `0x53cc60`, called at `0x4cb6d2` |
| bound the eight transformed points: min/max per axis, centre = (min+max)/2, half = (max-min)/2, then a radius | `fcom` min/max loop, `fmul [0x6032e0]` (the 0.5 constant) | `0x4d8bd0`, called at `0x4cb6eb` |

So the box is a **node-local axis-aligned bounding box** (min corner, max corner), and
its frame is the node's own local space: the engine carries it through the node's
world matrix and re-bounds it, centre first. That matches the owner measurement of
`docs/findings/2026-10-21-m01-objective-target-points.md` (the record point is the
composed transform applied to the box centre, to 0.05 m) and it is the reason a
rotated node gets a larger world-axis box than its local one.

Measured local boxes (min / max, metres, from `RawNodeInfo::unk164`):

| node | `unk164` min | `unk164` max | local size |
| --- | --- | --- | --- |
| `t_truck01`, `t_truck03` | `[-1.48, -0.17, -2.79]` | `[1.48, 4.45, 4.41]` | 2.96 x 4.63 x 7.20 |
| `bridge_truck01` | `[-1.92, 0, -13.60]` | `[1.92, 5.87, 3.97]` | 3.84 x 5.87 x 17.57 |
| `rock_zeppelin` | `[-53.17, -48.22, -222.89]` | `[53.17, 57.13, 348.69]` | 106 x 105 x 572 |
| `susp_bridge` | `[-5468.6, 72.1, -5683.0]` | `[-5451.4, 169.5, -5119.9]` | 17 x 97 x 563 |

All five are grouping nodes (`mesh_index = -1`, `unk112 = 2`); the box is the union of
the children, which is why the zeppelin and the bridge are as large as they are.
`susp_bridge`'s box is already in world coordinates (a zero-translation group).

## 2. What changed in the build

`mission_targets::target_bounds` replaces `target_point`: it carries the eight corners
of the first non-empty box through the node's composed world transform and returns the
bound's centre (unchanged: the target point) and half extents. `BoundTarget`
and `MissionGroundTarget` gain `target_half_extents_m`; `ground_target_sweep` builds the
swept box from it, with the previous designed `[5, 3, 5]` kept **only** for a node that
stores no box (`GROUND_TARGET_BOX_CLAIM`, still `designed`). A target that uses the
stored box carries `GROUND_TARGET_NODE_BOX_CLAIM` with class `inferred`.

## 3. Not proven (unknown, with the affected content)

* **That the original's gun hit test uses this box at all.** The image reads it in the
  database-intersection walk; this task did not trace the gun-round path to it. The
  swept box for gun hits is therefore `inferred`, not measured.
* **Grouping nodes are not narrow-phased by that walk.** The walk takes the box branch
  only when node flag bit `0x40` is set; the flag words of the five nodes above
  (`0x0308051c`, `0x0308851c` for `susp_bridge`) have it clear, so that walk recurses
  into their children instead. If gun hits use that walk, the group box is a broad
  bound, not the hit volume.
* **Affected content:** `susp_bridge` (a 17 x 97 x 563 m box) and `rock_zeppelin`
  (106 x 105 x 572 m) are bound ground targets whose swept boxes are now those volumes.
  Any round through the bridge's box destroys the bridge's one-unit designed pool, and
  `t_truck01` sits inside it (its target point is within the bridge's x/y/z range), so
  the earlier "1.1 m sliver" overlap of `t_truck03` with the bridge is, with the stored
  boxes, containment. Whether the original shot the bridge down from the trucks' fire is
  unknown; a follow-up task owns resolving which box (or the children's) the gun hit
  uses.
* The trucks' world box uses the node's composed rotation (what the engine does), but
  the swept box component is axis-aligned: a ground target spawns with identity
  rotation, so its box is the world-axis bound, not an oriented box.
