## 1. Where the records live, and the class they are parsed into

#770 §1 measured the load path: `0x439530`..`0x43968e` builds
`..\data\%s\%s\zrdr\aiv.zrd` (`0x62283c`), opens it (`0x579c60`) and stores
one 12-byte record per aircraft in the container at `0x64f620`
(`{count, array}`), each record `{+0: netid, +4: name copy, +8: document}`.
The document is a **CCEVeh** object: 0x158 bytes, vtable `0x6036fc`, ctor
`0x43bf10`, and its virtual 8 — **`0x437620`** — is the parse routine that
maps the record's positional fields into the document's fixed slots. The
per-record spawn loop is `0x474cd9`..`0x475335` inside `0x4735b0`, and the
vehicle loader is **`0x47c210`** (#770 already measured its heading
conversion at `0x47c4e5`).

Every retail record measured carries **81 positional fields** (M01: all 12
records; the count is also uniform across the 53 missions #676 surveyed). The
original's own format comment for this record class is committed inside the
executable at `.data` `0x622508` (805 bytes, quoted by #681): it names the
fields `netids (x y z) yaw team group enabled primary_target init_health …
title deactivated …`, and the parse routine corroborates the order below. The
document writes `netids` as a count (`+0x10`) plus an int array (`+0x14`),
accepting either a bare integer or a list of integers — exactly what the
comment's last paragraph says.

## 2. The measured field map

| field | meaning | parse site → document slot | consumer |
| --- | --- | --- | --- |
| 0 | **net ids** (int or list of ints) | `0x437685`..`0x4376ee` → `+0x10`/`+0x14` | loader `0x47c733`: when the count is one, `vehicle+0x2e4 = array[0]` — the slot `SET_AI_NET` writes and the wake path restores a position from (#681) |
| 1 | **position** `(x y z)` | `0x4376f0`..`0x437711` → `+0x18..+0x20` | loader `0x47c2a6` reads the vector, `0x47c4b3` applies it to the node (`0x4d1d50`) |
| 2 | **heading**, stored degrees | `0x47c4e8` (`fld [edi+0x24]`), stored by `0x437714` → `+0x24` | `0x47c4e5`..`0x47c4fa`: × the image's π/180 double (`0x6040e8`), `SetRotation(node, 0, yaw, 0)` — the committed `[heading]` row |
| 3 | **team** | `0x43771d` → `+0x34` | `0x47c674`: `0x453740(&slot, team)` + the base-class virtual `vtable+8` (`0x441b80`) → `vehicle[+8]`, the same setter `SET_AI_TEAM` reaches (#681) |
| 4 | **AI group** | `0x437726` → `+0x38` | `0x47c694`: `vehicle+0x388 = group` — the group `TRAVELERS` counts (#681) |
| 5 | **enabled** | `0x43772f` → `+0x3c` | spawn gate `0x474d10`: a zero value **skips the spawn entirely** (`je 0x475326`, the next record) |
| 6 | **primary target** (text) | `0x437738`..`0x43777a` → `+0x44` | `0x47c6a0`: non-empty text is `strdup`ed into `vehicle+0x2f8`; when absent and the vehicle's `+0x67c == 4`, the literal `player` is stored instead |
| 20 | **title** (text, usually a `MSG_*` key) | `0x437841`..`0x437869` → `+0x0c` | not consumed by the loader; runtime consumers unmeasured |
| 21 | **deactivated** | `0x43786c`..`0x437878` (`cmp [slot], 0; setne`) → byte `+0x40` | `0x47ca14`: non-zero → `0x4b0f40(vehicle, 1)` — **spawns the aircraft asleep** |

The remaining fields (`7..19`, `22..80`) are parsed into fixed slots
(`0x43777c`..`0x4379af` and beyond) but are **not measured** here; the
comment suggests `init_health`, the radius triples, the pilot-skill ratings
and the paint fields, and retail data is consistent with it (e.g. `bsfury_1`
carries 108.0 where the player carries 0.0), but no consumer was traced for
them in this task, so they stay unknown.

## 3. Airframe / vehicle type: it is not a field

Measured at the spawn loop, in order:

1. `player` (`0x474d1b`, case-sensitive literal): the airframe comes from the
   engine state — `0x71daec` in campaign mode or the scenario object in mode
   3 (#770 §2–§4). No record field is read.
2. `wingman_1` (`0x474e3e`): the vehicle template is matched against the
   airframe row's fifth pointer (`0x426d60`, the `model` field of the
   eleven-row table), falling back to `Devastator` when the global
   `0x71db4c` is the none value 11 (`0x474e76`..`0x474e85`).
3. `wingman_4` (`0x475016`): the player's own airframe is used only when
   chapter/mission is `c3`/`m05` or `c4`/`m04` (`0x47502c`..`0x4750a4`);
   otherwise it falls through to the generic branch.
4. **Every other name** (`0x4752a8`): `strrchr(name, '_')` truncates the
   record name at its last `_`, the prefix is compared case-insensitively
   (`_stricmp`) against the vehicle registry built from **`vehicle.zrd`**
   (opened at `0x474b5b`, member string `0x627b18`), the name is restored,
   and the matched template is handed to the loader `0x47c210` together with
   the record document. With no `_` in the name, or no registry match,
   nothing is spawned (`0x475303`).

So a scripted aircraft's vehicle type comes from its **record name prefix**,
never from a field — and the record's own name also becomes the vehicle's
registry key (`0x4d0280(name, 7)` at `0x47c234`, inserted at `0x47c537`),
which is how `WAKEUP_ENEMIES` finds `bsfury_1` by name.

Retail corroboration: the installation's common reader archive `ZBD/zrdr.zbd`
carries the vehicle-definitions document whose 150 records include
`bsfury`, `rusdevastator`, `devastator`, `wingman`, `pdevastator` and the
eleven `p*` airframe records — every prefix M01's twelve records truncate to.
What each vehicle record's own fields (model, `kind_of`, …) map to is
vehicle.zrd's layout, a separate measurement; the airframe *display* name of
an AI aircraft is therefore still one step removed, and that step is named in
Unknowns.

## 4. Initial sleep state, and how the program wakes it

* A record whose field 21 is non-zero is parsed with document byte `+0x40`
  set (`setne`, `0x437875`), and the loader puts the vehicle to sleep at
  spawn: `0x47ca14` → `0x4b0f40(vehicle, 1)`, which (#681 measured) sets
  `+0x945 = 1`, `+0x91d = 1`, `+0x91e = 0` and deactivates the node.
* The mission program wakes it with the `WAKEUP_ENEMIES` directive (#681):
  the wake handler `0x469b5b` resolves each name in the vehicle registry
  `0x71dab8`, checks the asleep byte `vehicle+0x945` (`0x469b91`) and calls
  `0x4b0f40(vehicle, 0)` — so the directive wakes only what the deactivated
  field put to sleep, and is a no-op for everything else.
* M01 spells `WAKEUP_ENEMIES` once — `OBJECTIVE13 [text bsfury_1, text
  blackswanzep]` — and `bsfury_1` is exactly the one M01 record whose field
  21 is `1`. The other eleven records carry `0` and start awake. This closes
  #1435's point 4: the wake path drives the aircraft records' own field.
* An aircraft whose field 5 (enabled) is zero is **not spawned at all**
  (`0x474d10`); M01's `bsfury_2` and `rusdevastator_3` carry `0` there. They
  are not "asleep records the program could wake" — the spawn loop never
  creates them.

## 7. Unknowns (each with its evidence)

1. **The airframe *display* name of an AI aircraft.** Measured: the vehicle
   record the name prefix selects (`bsfury`, `rusdevastator`, …). Not
   measured: what vehicle.zrd's own fields map that record to a `.flt`
   model / airframe row. Resolving: a vehicle.zrd layout measurement.
2. **Fields 7..19 and 22..80.** Parsed into fixed slots
   (`0x43777c`..`0x4379af`+), untraced consumers. The embedded comment
   suggests meanings; no consumer was measured, so none is claimed.
3. **The netids index space.** Measured: the single value lands in
   `vehicle+0x2e4`, the `SET_AI_NET` slot. Not measured: what entry the ids
   24..34 select — M01's own `net.zrd` has only 8 entries, so they are not
   indices into it, and the `nets\neindex.zrd` / `ne%06d.zrd` files
   (`0x621aa0`) are not in this installation.
4. **Team numbers' engine-wide meaning.** Measured: the value is written into
   the base team field. Not measured: what 1 vs 2 (or 0) mean for targeting
   and hostility.
5. **The meaning of the primary target to the AI.** Measured: the name is
   stored at `vehicle+0x2f8`, with the `player` default when `+0x67c == 4`.
   Not measured: what the AI does with it (attack target, formation leader,
   or something else).
6. **The header's leading scalar (51 in M01).** The `(id, name)` table's
   interpretation is #1432/#770-adjacent; the leading value's meaning is
   unmeasured.
7. **`title`'s consumers.** Measured: parsed into the document at `+0x0c`.
   Not measured: which runtime path reads a spawned vehicle's title.

## 8. Corrections and limits of this note

* The mapping in §2 is read from the parse routine's own instruction order —
  field slot `0x0c + 8*i` of the record's field array (`payload_i =
  [base + 8*i + 0xc]`, the copy loop at `0x4376b9`) — and every meaning is
  pinned by the *consumer* instruction, not by the embedded comment alone.
  Where the parser transforms a value that is recorded here rather than
  smoothed over: the field at slot `0x5c` is stored as `-|value|` when
  positive (`0x437797`), the one at slot `0x94` likewise (`0x43780a`), and
  the site between them (`0x4377d4`, slot `0x7c`) stores its raw value and
  then, when positive, overwrites it with the negation of the **neighbouring**
  slot `+0x68` — a site that reads a slot the same parse has not written yet.
  None of those fields is claimed; all stay unknown, and the odd site is
  recorded as measured.
* The `wingman_1`/`wingman_4` special cases are measured for the dispatch
  only; what template name the `0x426d60` accessor's string selects is the
  airframe row's fifth pointer (`w`, literally `wingman` on row 5), which
  corroborates but does not extend §3.
* Nothing here changes the standing refusals: `AIRFRAME_UNKNOWN_REASON` and
  `POSE_UNKNOWN_REASON` still hold for a document-only read; this task adds
  positive evidence for the *player's* airframe refusal (no field names one —
  the dispatch proves the airframe enters through engine state or the record
  name, never through a field) without relaxing it.
