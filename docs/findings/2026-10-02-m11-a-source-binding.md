# M11-A: the eleventh source-derived mission binding, and why M11 stays unbound

Date: 2026-10-02. Task: M11-A "Bind original mission data and branches"
(#288, `missions/M11.md`, work order `M11-A`). Shared contract:
`docs/contracts/SCRIPT-MISSION.md`; identity rules
`docs/contracts/IDENTITY-CONTENT.md`. Capabilities used: `retail`
(`$CS_GAME_DIR` read-only, never written), `synthetic`. Implementer:
**bunny-alpha-1** (session of 2026-10-02). No reviewer yet; the implementer's
own run is not independent review and no agent review replaces the owner's
human approval.

**The minimum acceptance scenario, *"Source-derived binding has no unresolved
critical dependencies"*, does NOT hold for M11, and no test in this stage claims
that it does.** M11's declared discovery title is carried by no localized row of
the installation, so four of the five critical dependencies are unresolved and
the mission, world and program identities stay `null`. Resolving them needs an
owner decision — Rally #470 `M05-A-GUIDE-TITLES`, recorded as `blocked` — so
this stage measures everything that can be measured and refuses the rest.

## What changed

Production (`crates/cs_content/src/campaign_bindings.rs`), one change:

- `unresolved_critical_entries(dependencies) -> Vec<String>` names every
  critical dependency that is not resolved, with the refusal that caused it, and
  `SourceContext::bind` extends `SourceBinding::unknowns` with those entries.
  The reason is that `SourceBinding::to_json` writes **no** dependency states:
  without this, `missions/bindings/M11.json` held three `null` identities, an
  empty `source_spans` and no sentence saying *why* — a record
  indistinguishable from one nobody had reached. A binding that resolves all
  five contributes nothing, so the records committed by M01-A … M06-A are
  byte-identical to before and their pinning tests still pass.

Tests and records: `crates/cs_app/tests/campaign/m11_a.rs` (eight
`accept_m11_a_*` tests), `missions/bindings/M11.json` (generated by
`SourceBinding::to_json`, pinned by a test), the M11-A harness in `evidence.rs`,
and a `missions/bindings/README.md` paragraph. Wiring only:
`crates/cs_app/tests/campaign/main.rs` (`mod m11_a;`).

**No comparison was loosened.** `title_form` stays exact, no fuzzy or
proximity rule was added, and `SourceContext::confirm_title` is unchanged.

## Why M11 cannot be bound from its declared title

`missions/M11.md` requires the title to be "confirmed against local strings",
and that confirmation fails. Measured from
`GOSDATA/ASSETS/BINARIES/langui.dll`:

| Row | Text |
| --- | --- |
| 3490 (bare short name, block `3480…3503`, offset 10) | `[AB14I]The Stolen Starlet` |
| 3460 (region-prefixed long name, block `3450…3473`, offset 10) | `[AB14I]Hollywood - Nathan Zachary & The Stolen Starlet` |

Both rows of **both** campaign-length blocks were visited:
`accept_m11_a_the_declared_title_is_carried_by_no_retail_row` asserts that
neither display text equals `The Stolen Scarlet` and that
`title_form(display, title)` is `None` for every one of the 48 rows. The scan
is not vacuous: the same scan over the same rows finds declared titles carried
by exactly one row *and* by two, and finds at least half of all 24 declared
titles.

The refusal is the title's, not the table's. `join_agreement()` is still
`Agreed` — the region-prefixed rows group into `[5,5,5,5,4]`, the same shape as
the chapter sizes — so a contradicting localized table is not the cause and
cannot be blamed for one. `campaign_position_for(None, …)` returns
`NO_CONFIRMED_ROW_REFUSAL`, and each of the three position-dependent
dependencies records that reason, while `title_string` records
`UNCARRIED_TITLE_REFUSAL`.

## What is different at M11

- **The discrepancy is one character, and the original agrees with itself.**
  The declared title and the retail spelling have the same words; exactly one
  word differs and it differs by exactly one character (`Scarlet` / `Starlet`,
  both seven characters). That is *measured*, not matched:
  `accept_m11_a_the_position_the_declared_order_would_select_is_read_from_the_installation`
  counts the differing word positions and the differing characters, and never
  asks any production function to treat the two strings as equal. It also
  asserts that the long name ends with exactly the string the bare short name
  gives, so the two structures of the installation describe one mission under
  one spelling — unlike M09, M14, M15, M20, M22 and M23, whose two rows differ
  in wording as well.
- **The declared order and the retail campaign order agree everywhere the
  strings carry a title.** This is new, and it is the evidence the owner
  decision rests on. `accept_m11_a_the_declared_order_agrees_with_the_retail_campaign_order_where_it_is_carried`
  runs the production `confirm_title` + `campaign_position_for` over **all 24**
  declared work orders: 17 are carried, and every one of the 17 selects its own
  index of `campaign-inventory.tsv`. The other seven are exactly
  `M09, M11, M14, M15, M20, M22, M23` — the set #470 already lists, now
  re-derived rather than repeated. One disagreement would have made the
  measurement say nothing about M11.
- **M11's declared index is a genuine boundary.** Offset 10 is chapter 3's first
  mission and the first row of the localized long names' third region group: the
  layout's chapter boundary and the region grouping put both boundaries on the
  same row, exactly as M06-A measured at offset 5. Its world group would be
  `world/c3`, which chapter 3's other four missions share, so neither the world
  id nor the mission number would identify the mission — only the position
  does. `ZBD/C3/M01/zrdr.zbd` exists.
- **Nothing of that is bound.** The test that measures it also asserts
  `campaign_position`, `catalog_id`, `world_id`, `program_id` are all `None` and
  that `source_spans` is empty, so it cannot be read as a binding. The join is
  per-title, never per-index: binding M11 with the spelling the installation
  *does* carry resolves all five dependencies and selects offset 10, and that is
  precisely the decision #470 has to make — it is measured, asserted and left
  unbound.

is `checked`.

## Why no spelling rule was added

Three routes were available and all three are refusals, not workarounds:

1. **Fuzzy or proximity matching** (`Scarlet` ≈ `Starlet`). Forbidden by
   AGENTS.md rule 4, and exactly what `…only_an_exact_title_or_an_exact_long_name_tail_confirms`
   asserts against — including M11's own shape.
2. **A declared per-work-order ruling inside `docs/findings/`.** That is the
   owner's call, not this session's: #470's blocked reason names (a) and (b) as
   the two routes and requires one of them from the owner.
3. **Editing `missions/README.md` / `campaign-inventory.tsv`.** Protected paths,
   `allowProtectedChanges=false`, and `crates/cs_app/tests/campaign/inventory.rs`
   asserts the two stay in sync.
